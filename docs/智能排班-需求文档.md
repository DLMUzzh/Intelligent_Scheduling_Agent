## 1. 项目背景与业务目标

车队长需要根据道路数据采集需求，将不同类型的采集任务分配给车辆和司机，并安排早、中、晚班次。人工排班需要同时核对资源可用性、司机效率、班次资格、车辆容量及已有安排，存在核对成本高、资源冲突和工作量不均衡等问题。

系统面向单车队、几十辆车的业务规模，由车队长通过页面或自然语言提交需求。系统生成排班预览，车队长检查、调整并确认后形成正式排班。

核心业务目标如下：

1. 降低任务创建、资源查询、自动排班及人工调整的操作成本。
2. 在资源和业务约束下尽可能分配采集需求，并清楚展示未分配量。
3. 资源不足时优先满足 TAG 需求，在各模式内部落实效率优先和工作量均衡目标。
4. 保留车队长对正式排班的最终决策权，所有生效操作均有明确的人工确认。
5. 通过 Agent 理解自然语言、调用业务工具并返回真实业务结果。
6. 保留正式排班、修改和取消记录，支持查询、统计及追溯。

## 2. 用户与首版范围

### 2.1 参与者

| 参与者 | 定位 | 职责 |
| --- | --- | --- |
| 车队长 | 唯一直接操作角色 | 管理采集计划、司机和车辆；生成、调整、确认及取消排班；查询统计与操作记录 |
| 司机 | 被安排资源及未来通知对象 | 首版不登录、不接单、不反馈执行结果 |
| Agent | 系统内部业务助手 | 在车队长权限内理解指令、澄清信息、调用业务工具、展示结果及待确认变更 |

### 2.2 纳入首版

- 单车队、固定车队长操作身份；Windows 本机免登录使用，页面与 Agent 共用同一业务范围。
- 采集计划及每日 TAG、ROAD 需求管理。
- 司机、车辆、班次资格、容量及整日不可用时间管理。
- 自动排班、可恢复的逐日预览草稿、人工调整、整计划统一确认；单日计划也按完整计划确认。
- 未来日期正式排班的单日修改、取消及重新排班。
- Agent 自然语言查询和受控业务增删改操作。
- 任务分配统计、排班历史、操作记录及数据持久保存。

### 2.3 首版不实施的内容

- 多车队、多个排班操作者、独立管理员端、司机端和多角色权限配置。
- 司机接单或拒单、实际出勤反馈、实际采集结果录入及实际完成率统计。
- 当天补排、执行中的自动换人或换车、小时级请假或维修时间管理。
- 路线规划、按采集类型或路况折算容量、系统自动评估司机效率。
- 任意 SQL、通用数据库管理以及同模块多条或跨模块批量修改资料；整计划确认和需求排班联合变更仍按专用业务规则处理。
- 多日正式排班批量修改。

### 2.4 通知 TODO

首版不实施实际通知，也不采用控制台模拟发送。通知发送、状态记录、失败重试及完整通知中心统一保留 TODO，页面只标明“通知未接入”。不得生成虚假的发送成功记录。

后续通知 TODO 保留以下业务背景：通知对象为对应司机，内容包括司机、车辆、采集日期、班次及任务包；只能由成功确认的正式排班触发，通知失败不应回滚已确认排班。这些内容不构成本次发送实现或验收要求。

## 3. 业务术语与输入输出

### 3.1 术语

| 术语 | 定义 |
| --- | --- |
| 采集计划 | 车队长创建的单日或连续日期范围内的采集需求集合 |
| 每日需求 | 某个采集日期下，各 TAG 或 ROAD 类别的目标量 |
| TAG 模式 | 按 Tag 类别和数量分配的任务模式，单位为“个” |
| ROAD 模式 | 按道路类型或路况类别和公里数分配的任务模式，单位为“公里” |
| 任务包 | 分配给一辆车一个班次的任务集合，可包含多种同模式采集类别 |
| 排班预览／草稿 | 尚未确认的候选安排；可保存和调整，不占用正式资源 |
| 正式排班 | 经车队长确认并生效的安排，参与资源占用和正式统计 |
| 未分配量 | 当日目标量中尚未安排的部分，不表示实际采集失败或实际未完成 |
| 累计排班次数 | 系统内有效正式排班的班次数，不表示实际出勤或实际工作完成次数 |
| 硬约束 | 无论自动排班还是人工调整都必须满足的合法性规则 |
| 优化偏好 | 自动排班用于比较合法方案的偏好；人工调整可以偏离，但不能突破硬约束 |

### 3.2 主要业务输入

- 单个采集日期，或包含起止日期的连续日期范围。
- 各日 TAG 类别与目标数量、ROAD 类别与目标公里数及排列顺序。
- 启用且可用的司机、司机效率等级、班次资格及请假日期。
- 启用且可用的车辆、每班 TAG 和 ROAD 容量及维修日期。
- 有效正式排班及其资源占用、司机累计排班次数。
- 人工调整内容、确认范围，或 Agent 解析后待确认的明确业务操作。

### 3.3 主要业务输出

- 按日期、车辆、司机、班次及模式组织的排班预览或正式排班。
- 任务包内各采集类别的分配量及对应容量占用。
- 按日期、模式和类别展示的未分配量及原因。
- 操作结果、冲突对象、失败原因和整计划确认结果。
- 任务分配统计、资源使用情况及变更历史。

## 4. 全局业务规则

1. 所有业务日期按北京时间（Asia/Shanghai）解释，日期范围包含首尾两天。
2. 同一采集日期只能归属一个计划；日期不重叠的多个计划可以同时存在。
3. 每天有早、中、晚三个班次，一辆车一天最多安排三个班次。
4. 一名司机一个自然日最多安排一个班次，不能同日驾驶两辆车。
5. 一个车辆班次最多一份任务包、一名司机；司机和车辆不存在固定绑定关系。
6. 同一车辆同一天只能采用 TAG 或 ROAD 一种模式，不同日期可以切换模式。
7. 同一任务包可以包含多种 Tag，或多种道路类别，但不能混合 TAG 与 ROAD。
8. 多种 Tag 数量直接相加，不能超过对应车辆班次的 Tag 容量；多种道路公里数直接相加，不能超过对应道路容量。
9. Tag 数量与道路公里数独立分配、独立统计，无固定换算关系，不能相加形成统一工作量。
10. 司机和车辆必须启用且在对应日期可用；司机须具备对应班次资格。
11. 各采集类别在同一天的分配总量不能超过该日目标量，分配数量必须为合法正数。
12. 司机效率等级为 HIGH、MEDIUM、LOW，只影响分配优先级，不改变车辆容量。
13. 自动排班先生成预览，不直接产生正式排班；预览编辑允许增删明细及修改司机、车辆、班次和任务数量。
14. 每次预览修改都校验硬约束；失败拒绝本次修改，保留修改前的完整预览。
15. 允许在需求尚未全部分配时确认有效排班；未分配量仅提醒，不自动进入其他日期、其他计划或下一次排班。
16. 新增排班以整个采集计划全部日期为确认范围，不支持从多日计划中选择单日或部分日期确认；全部待确认日期成功才生效，任一失败则本次新增确认全部回滚。
17. 整计划再确认时，当前仍有效的已确认日期只读保留，包括当天及过去的有效正式日期；其余日期必须是未来日期并全部通过校验。计划全部已经确认时返回 ALREADY_CONFIRMED，不重复创建正式排班。
18. 正式排班修改仅限未来日期。提交前展示全部差异，车队长明确保存后重新校验；成功才更新，失败完整保留原安排。
19. 生效内容必须与车队长确认的内容一致；Agent 不能在解析指令后自行使正式修改生效。

## 5. 功能需求

### 5.1 使用范围与计划生命周期（R01—R07）

| 编号 | 事项 | 确认需求 |
| --- | --- | --- |
| R01 | 使用者及访问方式 | 首版在 Windows 本机运行，车队长通过本机浏览器免登录使用，启动即进入工作台；固定车队长操作身份，兼任任务、司机和车辆管理，页面与 Agent 使用同一业务范围。不设置登录页、密码、登录会话或账号管理；司机不登录，不建设独立管理员端。开放其他访问范围须另行评审认证方式。 |
| R02 | 日期限制 | 以北京时间每日零点为界，只对未来日期创建、生成、确认和修改排班。采集日期当天及过去日期只读，不支持当天补排。 |
| R03 | 日期范围 | 起止日期均包含，统一使用北京时间；不设置未经业务确认的日期跨度硬上限。 |
| R04 | 计划状态 | 根据每日排班情况展示待排班、部分确认、全部确认、已取消及相应日期明细；首次确认整体成功或失败，不产生部分日期确认。未来按日取消后可出现部分确认，须列明有效及取消日期；不设置实际执行或实际完成状态。 |
| R05 | 计划删除 | 尚无正式排班记录的未来计划可以删除；存在正式排班历史的计划保留记录，通过取消未来安排处理。 |
| R06 | 日期重叠 | 新计划或日期调整与其他计划重叠时，整体拒绝并列出冲突日期，不自动合并或截取日期。 |
| R07 | 已确认日期迁移 | 不直接把正式排班移动到另一天；取消原日期安排后，为目标日期建立需求并重新排班，仍须满足日期唯一性。 |

补充说明：

- 日期锁定不依赖任务是否实际执行，也不自动把未确认排班转换为正式排班。
- “全部确认”表示计划日期的排班确认情况，不表示全部需求已分配，更不表示实际采集完成。
- 取消正式排班不删除计划的日期归属；需要重排时沿用原计划，不另建同日计划绕过限制。
- 整计划再确认中，仍有效的已确认日期只读保留；包含过期未确认日期时，整次新增确认失败，不能据此突破 R02。
- 整份计划编辑仅限全部日期仍为未来且从未有正式历史，包括名称、备注及日期需求范围；存在正式历史后，仅按既定规则调整未来单日需求或正式排班，不能借整体编辑迁移日期。

### 5.2 采集任务与需求输入（R08—R14）

| 编号 | 事项 | 确认需求 |
| --- | --- | --- |
| R08 | 每日需求 | 日期范围内默认复制相同需求，允许单独调整某一天，不改变其他日期。 |
| R09 | 采集类别 | Tag、道路类型及路况类别由车队长维护；道路类型或路况首版按采集类别名称管理，不增加容量折算规则。类别改名后未来需求及草稿显示新名称，当天及过去需求保留锁定前名称，已有正式排班及变更历史保留当时名称；类别被计划需求、草稿或正式历史引用时禁止删除。 |
| R10 | 数量与精度 | Tag 使用正整数；道路公里数为正数，最多三位小数。零表示没有该项需求，不生成任务；每个计划日期至少包含一项正数需求。 |
| R11 | 任务信息 | 包含采集日期、模式、采集类别、目标数量和可选备注；首版不提供路线规划。 |
| R12 | 同模式类型顺序 | 资源不足时，按计划中采集类别的排列顺序分配；车队长可调整排列顺序，不设置额外优先级权重。 |
| R13 | 需求拆分 | 同一类型需求可以拆给同日多辆车、多个班次；不能超出该日目标量，不跨日借用需求。 |
| R14 | 已确认日需求变更 | 仅限未来日期；允许在同一次操作中调整需求与受影响排班，统一检查、展示全部差异并保存，不允许已分配量大于变更后的需求；任一校验失败，两者均保留原数据。 |

任务包容量示例：

- 某车早班 TAG 容量为 100 个，Tag-A 40 个与 Tag-B 60 个可以放入同一任务包；合计 101 个则不合法。
- 某车早班 ROAD 容量为 80 公里，城市道路 30 公里与高速道路 50 公里可以放入同一任务包。
- 不能在同一任务包内同时分配 Tag-A 和城市道路；同一车辆当天其他班次也不能改用另一模式。

### 5.3 司机与车辆管理（R15—R23）

| 编号 | 事项 | 确认需求 |
| --- | --- | --- |
| R15 | 司机信息 | 姓名必填、联系方式选填；允许重名，通过唯一编号区分并定位。 |
| R16 | 效率等级 | 由车队长人工设置，新增司机默认 MEDIUM；系统不自动评估效率或计算评级分数。 |
| R17 | 班次资格 | 支持早、中、晚班资格配置，默认全部具备；不具备资格的班次禁止分配。 |
| R18 | 不可用时间 | 司机请假、车辆维修按整日登记，支持单日及连续日期范围，不支持小时级不可用。 |
| R19 | 车辆信息 | 车牌号必填且唯一，车辆名称或备注选填；维护启用状态及各班次容量。 |
| R20 | 零容量 | 允许某班次某模式容量为零，表示该班次不能执行该模式，不能向零容量模式分配任务。 |
| R21 | 资源删除 | 当前草稿、当前正式或任意正式历史引用司机/车辆时禁止直接删除，可先移除草稿引用再删除，或停用并保留关联。仅被统计容量快照引用不阻止删除，快照保留当时信息；没有排班引用时可删除。 |
| R22 | 资源变更影响 | 停用、请假、维修、资格变更或容量降低若导致未来正式排班非法，拒绝操作并列出受影响日期；先调整排班，再修改资源。 |
| R23 | 当天突发情况 | 当天临时请假、车辆故障由车队长线下处理；当天正式排班保持只读，首版不承担执行中的自动换人、换车。 |

资源规则补充：

- 车辆各班次分别维护 TAG 和 ROAD 最大容量；Tag 容量采用非负整数，道路容量采用非负公里数并遵循三位小数精度。
- 请假、维修、停用和班次资格均属于排班合法性判断条件，不能用效率高或任务紧急覆盖这些限制。
- 效率等级仅为优化偏好，修改等级不自动重排已经确认的安排。
- 未确认草稿不占正式资源；资源变更后，已有草稿按 R34 处理。

### 5.4 自动排班与衡量口径（R24—R31）

| 编号 | 事项 | 确认需求 |
| --- | --- | --- |
| R24 | 任务包与司机 | 一个车辆班次对应一份任务包和一名司机；同车同班不能重复建立任务包。 |
| R25 | TAG 优先 | 资源不足时先尽量满足 TAG，再用剩余资源安排 ROAD；各模式内部依次考虑任务覆盖、司机效率、车辆均衡、同等级司机均衡。 |
| R26 | 优化目标范围 | 不增加其他优化要求，保留已确认的效率优先和两类均衡目标，不取消均衡。 |
| R27 | 司机累计次数 | 统计系统内有效正式排班班次数；多日生成时临时计入本次前面日期已分配的班次。取消班次、其他未确认草稿不计，不代表实际出勤次数。 |
| R28 | 车辆均衡 | 按每天、同一任务模式下的容量利用比例尽量均衡；容量不同的车辆不要求数量绝对相等，TAG 与 ROAD 分开计算。 |
| R29 | 人工调整偏好 | 人工调整可以偏离效率与均衡偏好，但须满足全部硬约束；系统不强制改回自动方案。 |
| R30 | 同条件选择 | 日期按先后、班次按早中晚处理；其他条件相同时按稳定编号选择，相同输入的自动结果应可复现。 |
| R31 | 未分配解释 | 按日期、模式及类别展示未分配量和可确认的原因，包括司机不足、资格限制、车辆不可用、容量不足或车辆模式限制；不宣称结果一定为全局最优。 |

自动排班的优先关系为：

1. 在资源竞争中先考虑 TAG，再考虑 ROAD，不将两种单位合并比较。
2. 在各模式内部尽可能覆盖需求。
3. 在覆盖不受影响时优先 HIGH，其次 MEDIUM，最后 LOW。
4. 尽量均衡同模式车辆的容量利用比例。
5. 尽量均衡同效率等级司机的累计排班次数；其他高优先级目标不受影响时，优先累计次数较少者。
6. 条件相同再使用稳定的顺序选择。

首版采用贪心算法，并保留算法替换、优化的能力。本文只规定业务约束和优化目标，不规定具体接口、模块结构或算法代码。

各日需求独立分配；司机累计次数可以影响同一次多日生成中后续日期的选择，但不能把某日未分配需求移到其他日期。

### 5.5 预览、确认、修改与取消（R32—R42）

| 编号 | 事项 | 确认需求 |
| --- | --- | --- |
| R32 | 预览内容 | 展示日期、车辆、司机及效率等级、班次、模式、任务包明细、容量占用和未分配需求。 |
| R33 | 草稿保存 | 每个计划日期保留一份当前草稿，关闭页面后可恢复，暂不自动过期；先生成预览（允许为空）再手工编辑，不从未生成状态建立纯手工草稿；重新生成前提示将覆盖未确认的人工修改。 |
| R34 | 草稿与资源变化 | 草稿不占正式资源；计划或资源变化后提示需要重新校验，正式确认前使用最新数据检查，不静默替换司机或修改任务。 |
| R35 | 整计划确认粒度 | 首次确认覆盖整个采集计划全部日期及各日当前预览的全部有效明细；不支持从多日计划中选择单日或部分日期确认。每天必须有合法非空排班，允许需求尚未全部分配；只想保留部分任务包时，先调整逐日预览，再确认整个计划。 |
| R36 | 空排班 | 全部无法分配时仍展示需求和原因，但不能确认没有任何有效明细的排班。 |
| R37 | 整计划确认失败恢复 | 任一待确认日期失败，整次新增确认全部不生效，保留草稿并列出失败日期及原因，不自动忽略失败日期；修正后从整个计划重新提交。 |
| R38 | 正式修改范围 | 仅对未来正式排班按单日修改，采用全部差异展示及保存生效规则；不提供多日正式排班批量修改。 |
| R39 | 正式排班取消 | 未来日期允许按日取消，展示影响并明确确认；取消后释放司机、车辆占用，保留原需求及取消历史，允许重新生成。 |
| R40 | 取消后再确认 | 取消后的未来日期可重新生成预览，再从整个计划入口确认；仍有效的正式日期只读保留，包括当天及过去日期。所有待确认未来日期统一成功或回滚，不用历史确认记录阻止重排；过期且无有效正式安排的日期仍导致本次新增确认失败。 |
| R41 | 多页面旧数据 | 同一车队长的旧页面不能覆盖已更新数据；提交时发现内容变化则拒绝，要求刷新并重新检查。 |
| R42 | 历史信息 | 保留正式排班及后续修改、取消记录；司机、车辆、采集类别名称或效率等级变化不改写历史中的当时信息。 |

#### 5.5.1 整计划首次确认与部分需求

- 首次确认以完整采集计划为范围；单日计划整体确认，多日计划不支持选择单日或部分日期确认。
- 确认各日当前预览的全部有效明细；每日非空合法时，未分配量只作提醒，不导致整计划确认失败。
- 不设计同一天分多轮追加确认。首次确认后新增或调整安排，走未来正式排班修改流程。
- 不能通过保存空正式排班代替取消；如需清空有效正式安排，使用取消操作。

#### 5.5.2 整计划确认一致性

1. 确认范围固定为整个采集计划，不接受从多日计划中选择部分日期确认。
2. 首次确认检查计划全部日期；取消后再确认时，识别并只读保留当前有效的已确认日期，包括当天及过去日期，不重新计算或覆盖这些安排。
3. 对其余全部待确认日期重新检查日期边界、最新需求、资源可用性和全部硬约束；无草稿、空排班或过期未确认日期均为失败。
4. 所有待确认日期全部通过才一起生效；任一失败，本次新增确认全部回滚，原有有效正式安排不变。合法非空排班的需求缺口只提醒，不视为确认失败。
5. 失败后保留预览，并告知失败日期和原因，不自动忽略失败日或只提交成功部分。
6. 计划全部日期已经具有有效正式排班时，返回 ALREADY_CONFIRMED，不重复保存。

#### 5.5.3 未来正式排班修改

1. 选择未来日期的正式排班并编辑。
2. 展示所有拟修改字段的修改前、修改后内容，包括任何关联变化。
3. 由车队长明确执行“保存并生效”。该动作本身承担最终确认，不另设独立调整草稿和重复确认步骤。
4. 重新校验最新数据与硬约束，生效内容必须与车队长确认的内容一致。
5. 全部通过才更新；任一失败保留原正式安排，不发生部分修改。

正式修改与整计划确认是不同业务操作，不能使用后者“已有有效日期只读保留”的规则忽略正式修改请求。

### 5.6 Agent 自然语言操作（R43—R49）

| 编号 | 事项 | 确认需求 |
| --- | --- | --- |
| R43 | 操作边界 | 支持采集计划、排班、司机、车辆的业务操作及相关查询；通过预定义业务工具执行，不提供任意 SQL 或通用数据库管理能力。 |
| R44 | 可直接操作 | 查询、统计、生成排班预览可根据明确指令直接执行；生成预览不等于正式确认。 |
| R45 | 写入确认 | 新增、修改、删除业务资料，以及正式确认、取消排班，执行前展示完整摘要并由车队长明确确认一次；页面明确保存动作可承担确认，不重复增加步骤。 |
| R46 | 模糊指令 | 必要日期、数量缺失，或重名、目标不明确时先澄清，不猜测对象、不默认选择第一条记录。 |
| R47 | 相对日期及上下文 | 明天、本周等按北京时间解析，本周为周一至周日；写操作摘要展示具体日期和对象。范围包含只读日期时明确提示，不自动缩减操作范围。 |
| R48 | 批量写入 | 首版业务资料逐条写入，不支持同模块多条资料或跨模块批量修改；整计划排班统一确认及已确认日需求排班联合变更继续按专用业务规则执行。复杂请求可先拆解展示，再逐项执行。 |
| R49 | 结果真实性 | 依据真实执行结果回复，失败不能声称成功；写入结果不明时先查询核实，不盲目重复执行。 |

典型自然语言场景：

| 用户请求 | 预期处理 |
| --- | --- |
| 查询明天有哪些采集需求 | 查询并展示明确日期、各类型目标量及当前分配情况 |
| 查询目前所有高效率司机 | 返回真实司机资料；可用性须结合具体采集日期判断 |
| 将张三效率调整为高 | 确定唯一司机，展示原等级与新等级，确认后通过业务工具修改 |
| 创建明天的采集计划 | 补齐必要类型和数量，展示完整计划摘要，确认后创建 |
| 生成某个未来日期范围的排班 | 检查范围及所属计划，生成预览并展示未分配需求，不自动确认 |
| 把未来某班司机由张三换成李四 | 展示全部变更差异，明确确认后校验并保存，不能夹带其他修改 |
| 确认某计划排班 | 明确整个计划及全部日期，展示确认摘要，获得确认后执行整计划确认规则；仅指定多日计划中部分日期时，说明整计划范围并澄清，不静默扩大范围或执行部分确认 |
| 查询某日为什么未全部分配 | 返回可核实的数量缺口及限制原因，不编造资源状态或声称已经实际采集 |

Agent 的理解结果不能绕过业务硬约束、日期锁定或权限检查。自然语言入口与页面入口必须遵守同一业务规则。

### 5.7 查询、统计、页面及通知占位（R50—R54）

| 编号 | 事项 | 确认需求 |
| --- | --- | --- |
| R50 | 统计指标 | 展示各类型需求量、已分配量、未分配量和分配率，司机排班次数，车辆班次使用率及同模式容量利用率；不提供实际采集完成率。 |
| R51 | 查询筛选 | 支持日期或日期范围、计划、司机、车辆、效率等级、确认状态及未分配情况筛选。 |
| R52 | 操作记录 | 关键写操作记录操作者、时间、页面或 Agent 入口、操作对象、变更内容、成功或失败及原因。 |
| R53 | 页面范围 | 覆盖采集计划、车队资源、排班预览与正式排班、Agent 对话、统计与操作记录；不单独建设司机端或多角色权限配置页面。 |
| R54 | 通知占位 | 通知发送、状态和重试保留 TODO；页面仅标注“通知未接入”，不生成虚假成功状态，不建设完整通知中心。 |

统计口径：

- 统计需求量包含筛选范围内全部计划需求，包括尚未确认、仅有草稿及已取消日期；正式已分配量只计当前有效正式排班。草稿分配情况单独标注，不能把草稿与正式排班重复相加。
- 某日某类别未分配量为该日目标量减去当前展示口径下的已分配量。
- 分配率为已分配量除以需求量；无该类需求时显示不适用。
- TAG 可按数量汇总、ROAD 可按公里数汇总，两种模式分别展示，不相加计算总工作量。
- 司机排班次数统计有效正式班次，取消班次不计，不代表实际出勤。
- 车辆班次使用率反映已安排班次与可用班次的关系；同模式容量利用率为该模式正式已分配量除以全部符合条件的可用容量，包含未使用的可用班次容量，不仅统计已安排班次的容量。例如 10 个可用班次各容量 100，仅安排 2 班合计 160，该模式容量利用率为 16%，而不是 80%。
- 可用容量只依据车辆自身条件：启用、当日无维修、该班该模式容量大于零；不因司机不足、资格限制或车辆已排另一模式扣减。可用班次为至少一种模式容量大于零且车辆启用、当日无维修的班次。
- 建立计划时保存各日期的全部车辆班次容量与可用性，资料及维修变化只刷新未来日期，当天及过去冻结；未确认、仅草稿及取消日期同样保留基准。每次正式确认、修改另存当时快照。纯统计容量快照不阻止无排班引用资源的删除。
- 车辆均衡按每日、同模式比较；历史统计保留当时信息，不因当前资源资料变化而改写历史。
- 整体需求、未分配量和分配率按日期、计划、类别/模式筛选；司机及效率筛选用于司机班次数、车辆筛选用于车辆使用指标。排班历史的资源筛选定位包含该资源的日期，不把全队需求当成司机个人目标。
- 排班已确认、需求已分配和实际采集完成不得混用，首版只管理前两者。

## 6. 数据保存与性能要求（R55—R56）

| 编号 | 事项 | 确认需求 |
| --- | --- | --- |
| R55 | 保存及初始化 | 司机、车辆、计划、预览草稿、正式排班及操作记录重启后保留。新版本首次使用为空业务数据，演示数据与正式数据区分；不迁移旧数据库，旧文件原样保留，不自动导入旧演示数据。 |
| R56 | 性能验收 | 以 50 辆车、150 名司机、31 天、每天 10 类任务作为验收样例，排班计算目标不超过 5 秒，不包含模型等待时间；样例规模不是业务上限。 |

性能验收应记录运行设备、样例数据和计时方式。5 秒为本次确认的验收目标，不表示当前实现已经达标；自然语言模型响应时间与排班计算时间分别记录。

## 7. 核心业务流程

### 7.1 创建计划至正式确认

1. 车队长打开本机应用，无需登录；维护司机、车辆、班次资格、容量及不可用日期，操作统一归于固定车队长身份。
2. 选择未来单日或连续日期范围，配置每日 TAG、ROAD 需求。
3. 校验日期唯一性、数量和类别，明确保存后创建计划。
4. 生成排班预览，展示任务包、容量占用、未分配量及原因。
5. 车队长按需增删或调整预览；每次修改校验失败均保留原预览。
6. 从整个计划发起确认，检查全部计划日期及各日安排摘要并明确提交；不提供选择部分日期确认。
7. 全部待确认日期校验通过才一起形成正式排班；任一失败则本次新增确认全部回滚，保留草稿及失败原因。成功后更新正式统计和操作记录。
8. 通知保持 TODO，展示未接入，不执行实际发送。

### 7.2 修改未来正式排班

选择未来单日的正式排班 → 编辑；若同时变更需求，则与受影响排班一起调整 → 展示全部变更前后差异 → 车队长一次保存并生效 → 使用最新数据重新校验 → 全部成功才统一更新，失败保留原需求与安排 → 记录操作结果。

### 7.3 取消及重新排班

选择未来单日 → 展示取消影响 → 车队长明确确认 → 取消该日当前有效安排并释放资源 → 保留计划需求和历史 → 在原计划中重新生成预览 → 从整个计划发起再确认，已有有效日期只读保留，全部待确认未来日期统一成功或回滚。

### 7.4 资源变更

提交资源变更 → 检查未来正式排班影响 → 若导致非法则拒绝并列出影响日期 → 先调整相应排班 → 再提交资源变更。未确认草稿提示重新校验，不自动替换人员或车辆。

### 7.5 Agent 写操作

理解指令 → 定位对象与具体日期 → 缺失或歧义信息先澄清 → 展示完整拟执行摘要或变更差异 → 车队长确认 → 调用业务工具并校验 → 返回真实结果 → 记录关键操作。

## 8. 异常与一致性处理

| 场景 | 必须满足的处理结果 |
| --- | --- |
| 新计划与已有日期重叠 | 整体拒绝，列出冲突日期，不自动合并 |
| 数量为负、格式错误或超过精度 | 拒绝并指明错误，不产生部分保存 |
| 司机重复占用、资格不符或资源不可用 | 拒绝非法安排，保留修改前数据 |
| 车辆同日混合模式或任务包超容量 | 拒绝，不因效率或人工调整而放行 |
| 资源不足但存在有效安排 | 展示合法的部分预览及未分配量，允许确认有效安排 |
| 全部无法分配 | 展示缺口和原因，不确认空排班 |
| 整计划确认中任一待确认日失败 | 本次新增确认全部回滚，原有有效正式排班不变，草稿保留；合法非空的需求缺口不算失败 |
| 计划全部日期均已有有效正式排班 | 返回 ALREADY_CONFIRMED，不重复创建记录 |
| 提交前跨越采集日零点 | 按提交时日期边界检查，不能突破当天只读限制 |
| 草稿生成后资源变化 | 提示重新校验，确认失败时不静默重排或提交部分日期 |
| 旧页面提交过期内容 | 拒绝覆盖，要求刷新并重新检查 |
| 修改内容与确认摘要不一致 | 不允许生效，不能只检查安排合法性而忽略变更范围 |
| Agent 目标不明确 | 先澄清，不猜测、不执行写入 |
| 写操作结果未知 | 查询核实后回复，不直接重试造成重复记录 |
| 当天突发故障或请假 | 按首版范围线下处理，不改写锁定的正式排班 |

## 9. 验收标准

以下为待实施的验收用例要求，不是现有测试通过记录。

| 编号 | 场景与操作 | 预期结果 |
| --- | --- | --- |
| AC01 | 单日及连续日期范围创建，范围内调整单日需求 | 首尾日期均包含，允许单日差异；其他日期不受影响 |
| AC02 | 建立两个日期不重叠的计划，再提交重叠计划 | 前两个可并存；重叠请求整体拒绝并指出冲突日期 |
| AC03 | 创建或修改当天、过去日期安排；未来日期在提交前跨零点 | 当天及过去日期只读；提交时重新检查边界 |
| AC04 | 一个 TAG 包分配 40 个 Tag-A 和 60 个 Tag-B，容量为 100 | 合计 100 合法；合计 101 拒绝。ROAD 多类型公里数同理 |
| AC05 | 使司机同日两个班次、车辆同班重复安排或车辆同日混合模式 | 均拒绝，原数据完整保留 |
| AC06 | 选择请假、停用、维修资源或不具备班次资格的司机 | 不能分配；不能用效率优先覆盖这些硬约束 |
| AC07 | 资源充足的单日及多日任务 | 生成符合硬约束的预览，展示各类分配量、容量占用和缺口 |
| AC08 | TAG、ROAD 竞争不足资源，同模式存在多类型需求 | 执行 TAG 优先及类型排列顺序，未分配量不跨日滚入 |
| AC09 | 比较不同效率及同等级累计次数不同的司机 | 覆盖不受影响时优先高效率；在既定目标顺序下体现同级累计次数均衡；效率不改变容量 |
| AC10 | 同模式车辆容量不同并进行人工调整 | 自动方案按容量利用比例尽量均衡；合法人工调整可偏离优化偏好 |
| AC11 | 编辑预览，构造超容量或资源冲突；全部需求无法分配 | 非法修改拒绝并保留旧预览；空预览展示原因但不能确认 |
| AC12 | 多日计划每天有合法非空排班但部分需求未分配，尝试只确认一天，再确认整个计划；确认后追加安排 | 部分日期确认不允许；完整计划可整体确认，未分配量只提醒；追加走未来单日正式修改 |
| AC13 | 整计划首次确认中一天无草稿、空排班或冲突；取消后整计划再确认中一个待确认日失败，同时包含仍有效的已确认日期 | 两种场景均为本次新增确认全部回滚；原有有效日期不变，草稿与错误原因保留，不忽略失败日 |
| AC14 | 对全部日期均有效的计划重复发起整计划确认 | 返回 ALREADY_CONFIRMED，不重复建立正式记录 |
| AC15 | 修改未来单日正式排班；同次降低需求并调整受影响分配；另构造校验失败或摘要仅确认换司机但实际还改任务数量的请求 | 合法的需求与排班联合变更统一生效；任一失败均保留原需求与安排；不允许夹带变更，成功内容必须与完整确认内容一致 |
| AC16 | 取消未来单日正式排班，在原计划重新生成并从整计划再确认；计划同时包含过去仍有效日期 | 释放被取消日资源、保留需求和历史；已有有效日期只读保留，待确认未来日期统一成功或回滚；旧历史不阻止重排 |
| AC17 | 停用、请假或降低容量会使未来正式排班非法 | 拒绝资源变更并列出影响日期，先调整排班后才能变更 |
| AC18 | 两个页面先后修改同一安排 | 后提交的过期内容不能覆盖新数据，要求刷新检查 |
| AC19 | Agent 遇到重名、模糊日期、部分日期确认指令、同模块或跨模块批量资料写入、执行失败 | 遵守范围与确认要求；资料逐条写入；整计划确认范围不静默扩大；不猜测、不任意执行 SQL、不虚报成功，结果未知先核实 |
| AC20 | 查询含未确认及取消日期的统计、取消班次、修改资源或类别名称；某模式 10 个可用班次各容量 100，仅安排 2 班合计 160 | 全部筛选内计划需求计入基数，正式与草稿分开统计；取消班次不计累计；历史保留当时资源及类别名称，被需求、草稿或正式历史引用的类别禁止删除；无实际完成率，容量利用率为 16% |
| AC21 | 首次本机打开应用、关闭页面、重启系统及新版本初始化 | 免登录进入、操作身份固定为车队长；草稿和正式业务数据可恢复；新版本为空业务数据，旧库保留且不自动迁移，演示数据与正式数据区分 |
| AC22 | 确认排班后查看通知区域 | 只显示通知未接入；不实际发送、不生成虚假成功记录、不运行重试 |
| AC23 | 使用 R56 指定规模生成排班 | 排班计算不超过 5 秒，模型等待单独计时，并记录验收环境 |

## 10. 后续设计约束

1. 后续总体设计、数据库设计、API、Agent 工具及页面交互必须能追溯到本需求基线。
2. 页面入口与 Agent 入口使用相同的权限、日期边界、约束校验和正式生效规则。
3. 预览保存与正式排班生效必须在业务含义上区分，不把保存草稿解释为已确认。
4. 正式修改、首次确认、取消及重新确认的含义必须区分，不能因复用流程而改变既定规则。
5. 通知保持 TODO；司机反馈、实际结果及完成统计不作为首版隐含扩展。
6. 本文不新增其他待决策业务项。后续如发现确需改变本基线的规则，应单独说明影响并由用户确认后更新文档。
